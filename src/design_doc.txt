>>    2) A few bullets or sentences about each data structure describing:
>>    	a) how it is populated,

Every page of every segment in the executable is “lazy loaded”, meaning an spt_entry is made for every page and added to the supplemental page table for the process.
An initial stack page is allocated in setup_stack(), lazy loading happens in load_segment(), and stack growth page allocation happens in check_and_grow() which is called from check_addr() and page_fault().
spt_entries are created using spte_init().

>>        b) how it is accessed,

spt_entries are accessed using spte_lookup(), which finds the corresponding spt_entry in the process's supplemental page table for the given user address.
spte_lookup() is used throughout the code. Some examples include page_faults() which will find the entry for faulting addresses, and check_addr() and pin_buffer_pages() which check syscall buffers. Eviction reaches an entry through ft_entry->page.
The supplemental page table is accessed to add spt_entries when they’re created and it is destroyed (along with the spt_entries) when the process exits.

>>        c) how it is destroyed,

If frame_alloc() or pagedir_set_page() fails, the entry stays in the table and is freed when the process exits.
Overall, when a process exits through process_exit(), the hash_destroy() function calls free_spte() on every spt_entry in the process’s supplemental page table before the page directory is destroyed. The free_spte() function waits on the entry’s spte_lock and then frees the associated frame or swap slot and the spt_entry itself after.

>>        d) the expected size of that data structure,

4 + 8 + 2 + 2 + 12 + 3 + 1 + 4 + 4 + 24 = 64 bytes
uaddr, hash_elem,  2 bools, padding, 3 uint32_t, 3 bools, padding, file, swap_slot, lock

>>	e) how many of that data structure you expect to exist in your system, and 

There will be one table per process and with as many entries as there are pages in the code, stack, and data/bss segments of the process’s executable.

>>        f) how many processes could potentially touch that data.

Only the owning process and any process that evicts one of its pages (it updates is_loaded, swapped, and swap_slot). Synchronization is implemented during the eviction process to ensure that spt_entries stay isolated from each other even if Process B ends up using a frame that previously belonged to Process A. Both hold the entry’s spte_lock.


---- ALGORITHMS ----

>> A2: What data will be necessary when a process page faults in the 
>> code segment? How will your implementation locate that necessary data?
>>

For loading a page, we need to know whether it’s in a swap slot in disk, backed by a file, or if it’s an all-zero page (BSS or stack page). This data exists in the spt_entry for that page, which we get by hashing, because our supplemental page table is stored as a hash table. If the spt_entry doesn’t exist, we check to see if this is a valid stack access (if the fault was in kernel context, we use the saved_esp field in the struct thread, which syscall_handler() sets when a system call starts). If it is a valid access, we grow the stack by allocating a page and adding an entry to the process’s supplemental page table (else we just bad_exit()).

If the spt_entry did exist, we call alloc_and_load(), which does most of the work. It will allocate the frame (frame_alloc()), bring in the data from swap if it was swapped (using free_slot()), or use file_read_at() to read from the file in the spt_entry. Otherwise, if it was an all-zero page, the allocated frame is just zeroed out using memset(). After, pagedir_set_page() is used to connect the spt_entry’s uaddr to the frame’s kvaddr, so the address does not have a page fault next time it is accessed.

>> A3: How will your code coordinate accessed and dirty bits between
>> kernel and user virtual addresses that are aliases for the same
>> frame, or alternatively how do you plan to avoid the issue?
>>

We check the accessed and dirty bits of the user address using the owner thread’s pagedir and uaddr. The kernel writes only through kvaddr (which belongs to the frame and not to any specific spt_entry) while loading a page. File and zero pages can be reloaded so they should stay clean. A page loaded from swap has its slot freed, so we call pagedir_set_dirty() on it to make the eviction save it again. System calls touch user buffers through user addresses so the hardware sets the user bits. 

---- SYNCHRONIZATION ----

>> A4: When two user processes both need a new frame at the same time,
>> what race conditions are possible?  How will they be avoided?
>>

We put a lock (frame_lock) on the alloc_frames list so that only one can edit it at one point. Otherwise, we might have a race condition where two user processes try to add or remove frames from the list at the same time and corrupt the linkage. Essentially, the size and contents of alloc_frames have to stay constant while a process is accessing it so we do not end up with non-deterministic behavior from the list.c functions.

Two processes could also pick the same victim during eviction, or one could even evict a frame another is still creating. To avoid this, frame_lock is held while choosing a victim in frame_eviction() and the victim is pinned and unmapped before the lock is released so that the other processes skip it. Additionally, a new frame is pinned with its owner set before its added to the list so it cannot be evicted/touched before it is completely ready.

---- ALGORITHMS ----

>> B3: When a frame is required but none are free, some frame must be
>> evicted.  Describe your algorithm for choosing a frame to evict.
>>

We use the four given evictions priorities for NRU:
Priority 1: not referenced, not modified
Priority 2: not referenced, modified
Priority 3: referenced, not modified
Priority 4: referenced, modified

frame_eviction() makes up to three passes over alloc_frames and skips the pinned frames. Pass 1 only takes a priority 1 frame and breaks out of the loop if it finds one. Passes 2 and 3 take priority 2 frames and pass 2 clears the accessed bits so referenced frames (priority 3) can qualify in pass 3. The victim’s spte_lock must be free (meaning the page that currently has the frame is not accessing it) otherwise we fall back to the last unpinned frame scanned.

>> B4: When a process P obtains a frame that was previously used by a
>> process Q, how will you adjust the page table (and any other data
>> structures) to reflect that Q no longer has the frame?
>>

Under the frame_lock, Q’s PTE is cleared with pagedir_clear_page() and Q’s is_loaded is set to false. If Process Q’s page was evicted into swap space, the information in the supplemental page table for Process Q will be updated to reflect that. The ft_entry then points to P’s spt_entry with the owner set to P, and P maps the frame with pagedir_set_page().

>> B5: Explain your heuristic for deciding whether or not page fault 
>> for an invalid virtual address should cause the stack to be extended.
>>

In syscall.c, we have a check_and_grow() function. It only grows for user addresses with no spt_entry. We set a max size for the stack (which is 8 MB according to project details), and if the address is within that, we check if it's above our border (esp - 32) and then extend the stack. We use the 32 because the details mention a PUSHA instruction that can validly fault up to 32 bytes below the stack pointer. For kernel faults during the syscalls, we used saved_esp which is set at the beginning of syscall_handler() before the user-to-kernel mode switch.

---- SYNCHRONIZATION ----

>> B6: Explain the basics of how you plan to manage synchronization in your VM
>> design.  In particular, explain how it will prevent deadlock. 
>>

We have locks on important data structures and entries. frame_lock for the frame table, spte_lock for one per page (held while that page is loaded or evicted), swap_lock for the swap bitmap, and lock_file as the global file system lock.

Deadlock could occur in eviction if a process holds frame_lock while waiting on a page’s spte_lock, but another process is holding that spte_lock and while waiting on frame_lock. The only nesting that we have is spte_lock then frame_lock. We need synchronization to ensure that if a process realizes that another process has the lock to a frame it needs, it needs to move on rather than waiting to acquire that lock. We do this with lock_try_acquire() on spte_lock in frame_eviction(), so eviction never waits while holding frame_lock. Swap and file I/O happen after frame_lock is released so other page faults can continue. swap_lock is only held around bitmap updates. Buffers are pinned before read() and write() take lock_file, and alloc_and_load() only takes lock_file if it doesn't already hold it. 

>> B7: A page fault in process P can cause another process Q's page
>> to be evicted.  How will you ensure that Q cannot access or modify
>> the page during the eviction process?  How will you avoid a race
>> between P evicting Q's page and Q faulting the page back in?
>>

When P evicts Q’s page, P will hold frame_lock only while choosing the victim. It takes the victim’s page’s spte_lock with lock_try_acquire, so it skips any page that is busy and never blocks while holding frame_lock. Under frame_lock, P pins the frame (locked = true), calls pagedir_clear_page() on Q’s page directory, sets Q’s is_loaded to false, and sets the frame to point at P’s spt_entry instead of Q’s. From now, Q cannot read or modify the page, and any access will page fault. P then releases frame_lock and, if the page was dirty, writes it to a swap slot and records the slot in Q’s spt_entry (swapped = true). Only after that does P release Q’s spte_lock.

If Q were to fault the page back in during this, alloc_and_load() will first acquire the page’s spte_lock, leading Q to block until P finishes writing. Q then sees that swapped is true and reads the page from swap. If Q exits instead, free_spte() blocks on the same lock before freeing the slot, and process_exit() frees Q’s frames before destroying its page directory, so P never touches a destroyed page directory. 


>> B8: Suppose a page fault in process P causes a page to be read from
>> the filesystem or swap.  How will you ensure that a second process Q
>> cannot interfere by, for example, attempting to evict a page while it is
>> still being read in?
>>

While P reads a page in from the file system or swap, it will hold that page’s spte_lock and the corresponding frame will be pinned. frame_alloc() is called with locked = true, and page_fault() unpins it only after the page is mapped. frame_eviction() skips every pinned frame, and it only evicts a page whose spte_lock it gets with lock_try_acquire, so Q cannot pick P’s frame while it is being filled. 

For read() and write(), pin_buffer_pages() loads and pins every page of the user buffer before the file operation starts, and unpin_buffer_pages() unpins them afterwards so that the kernel never faults while holding the file system lock. The disk I/O will happen without holding frame_lock, and Q's own page faults can still proceed while P waits.
